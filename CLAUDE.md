# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Music Fighter" — a real-time, arena-style music battle app for **private gatherings among friends** (not bars/venues). A host creates an arena, participants join with a code, and songs face off head-to-head while participants vote from their phones. A separate "stage view" renders the battle on a shared screen (TV/projector).

This is a **Lovable** project: it is edited both locally and via the Lovable web editor (lovable.dev), and changes from either side sync through this git repo. `.lovable/plan.md` holds the description of the most recently applied Lovable change — treat it as a scratch note, not documentation, and expect it to be overwritten/irrelevant across sessions.

## Business Rules (from project spec, not inferable from code)

- **Change of focus (user decision 2026-10-27, after Spotify's Developer Policy) — overrides the spec docs wherever they disagree; full list of obsoleted spec parts in `docs/MVP_ROADMAP_2026-10-26.md` → "Change of focus":** (1) private gatherings, not venues — ignore spec wording about "local", venue history, GPS/geofencing, Stage View authenticating "the venue's account"; (2) Music Fighter **never plays audio**: it curates a playlist it creates in real time in the **host's Spotify Premium account**, played by the host's own Spotify app/device; (3) **participants never connect Spotify for taste/affinity** — affinity/passive voting will come from Music Fighter's own data (steps 8+9 **built** 2026-10-27, see "Own affinity & passive vote" below — signals = MF votes/proposals/likes only, Spotify↔open data bridged by ISRC → MusicBrainz, v0 rules then own model, never Spotify metadata in the profile/model (policy III.13/III.14); step 13 **built** 2026-10-28, see "System songs that fit the arena" below); since step 7 a member's *own* connection may be used in any arena **only to propose** (own search + own playlists, see "Proposing with your own Spotify"); (4) **Jukebox Boost and all payments are excluded** (steps 10-11). Spotify's own data limits also apply: no audio features/recommendations (closed to new apps), no `popularity` and no `product` on `GET /me` (Feb 2026), search `limit` ≤ 10, no `market=from_token` (needs `user-read-private`, which we don't request: 403 "Insufficient client scope"), `/playlists/{id}/items` (not `/tracks`), `POST /me/playlists`, dev mode = 5 allowlisted users. Spotify brand rules for any UI showing Spotify content: Spotify logo next to the metadata, artwork uncropped/uncovered, "OPEN SPOTIFY" link back, no crossfade/mixing (policy III.7).

- **Host powers (step 19b, user decisions 2026-10-30, `supabase/sql/host_powers_2026-10-30.sql`):** the host creates the arena (mood, warm-up = the "initial song"), Start battles / End Arena (= battle mode on/off), and plays the music from their own Spotify app. **MF has no playback controls** (no manual arena pause/resume, no play/pause/skip/device; pause/resume stay automatic, step 6, + "Resume on Spotify") and **no excluded genres** (not adopted: censorship). The host never starts single battles, picks pairs, vetoes/withdraws others' songs, touches votes or results, and sees nothing different in a draw (Block 5 §2.1, v4 §10.1): no client may write `battles`, `arenas`, `songs`, or update/delete `queues`; a client vote must be its own participant's (`votes_insert_own_participant`). Keep it so: any new host action goes through an RPC that can't choose songs/pairs/winners.
- Arena states: waiting → active → finished, plus technical expired (Backend_Block_2 §1). Backend-only transitions: `create_arena` (→ waiting, mood required), `start_arena_battles` (host, waiting → active), `end_arena` (host, waiting|active → finished), `arena_expiry_job` cron → `expire_stale_arenas` (waiting idle 6h → expired; active idle 2h → finished, except the curated-library arena). "Idle" = no participant activity (joins, proposals, votes — battles don't count, the cron creates those). Finishing an arena closes its open battle: kept if already decided at lock-in, else `resolution_type = 'cancelled'` (no winner, nothing queued). Retention (Block 5 §6): `arena_vote_purge_job` daily snapshots each battle's `final_votes_a/b` and deletes individual votes 30 days after a finished/expired arena closes (`arenas.votes_purged_at`). Enforced server-side by a battles-insert trigger (battles only in active arenas) and restrictive RLS (votes only in active; joins/proposals only in waiting|active; expired hidden). Definitions: `supabase/sql/arena_state_model_2026-10-26.sql` + `arena_lifecycle_closure_2026-10-26.sql`. `arenas.mood` is fixed at creation and is UX/copy only — never let it affect battle rules.
- **Warm-up song (user decision 2026-10-26, overrides Backend_Block_2 §4 / Block_4 §2 "warm-up always ends before the first battle"):** the host picks it at creation from **Spotify search** with their own account (free search, no mood suggestions: Spotify has no recommendations for new apps), so creating an arena requires a connected Spotify (`spotify-host` action `create_arena` → service-only `create_arena_spotify`; the old library `create_arena`/`get_warmup_suggestions` are dropped). It is silent in the lobby. `start_arena_battles` (returns the open battle id and creates battle 1 itself; the old `create-battle` Edge Function was deleted in step 19b) sets `arenas.warmup_started_at` and battle 1's `duration_ms` = the warm-up's duration — the warm-up is the "winner of battle 0", playing during battle 1, the same rule the cron applies afterwards (duration = previous winner). Stored as the arena's own `songs` row with `role = 'warmup'`; triggers reject it in `queues`/`battles`, and it never scores/PI. The same track can coexist as a competitor row (`songs_unique_per_arena` includes `role`), but since step 12 proposing it is refused in the lobby (`is_warmup`) and for 60 min after it starts (`recently_played`). Since step 6 it is the **first track of the arena's private Spotify playlist**, playing on the host's device (see "Playback" below); the browser MP3 is gone (`useArenaWarmup` is display-only). The curated library (placeholder `spotify_track_id`s) is retired since step 12b; battle 1 with nothing proposed takes the host's backup music. Definitions: `supabase/sql/warmup_song_2026-10-26.sql` + `spotify_playback_2026-10-27.sql`.
- Battle states: pending → active → closing → completed. Backend-only transitions via SQL RPC + cron (`battle_lifecycle_job` → `process_battle_lifecycle`, every second).
- Sudden Death: triggered when closing + tie at lock-in; lock-in is at end − 25 s and Sudden Death lasts 15 s, to end − 10 s, when it is resolved, so the winner reaches the Spotify playlist (and Spotify's own queue) before the song ends; the last 10 s take no votes (user decisions 2026-10-28, over v4 §5.3's −15 s/−5 s: a winner appended ~1 s before the end was missed by Spotify, `supabase/sql/radio_lead_in_2026-10-28.sql`). Only sudden_death vote_type accepted; one immutable vote per participant; a prior regular vote can be upgraded once, never downgraded.
- Draw resolution: if still tied after Sudden Death, current spec (v3.2/v4) sends both songs to the queue in A-B order. Do not implement the older v3.0 tie-break logic (PI level, then random) — it's superseded.
- Vote types: "regular" (active phase) and "sudden_death" (closing + sudden_death_active). Regular votes can be toggled/switched; sudden_death votes are final once cast.
- Passive-vote rules were decided by the user on 2026-10-27 (roadmap step 9: ≥75 % **pasivos**, k=1.25 cap lifted when there are 0 active votes, ≥0.7 threshold scaled 0.4→0.5 PB (0.5→0.6 with ≥75 % pasivos), 30 s ramp, 0 in Sudden Death). **Eligibility changed by the user 2026-10-28** (`supabase/sql/passive_vote_everyone_2026-10-28.sql`): not only PASIVO but **everyone present who hasn't voted** — ACTIVO, PASIVO, and INACTIVO only for lack of heartbeat (locked phone, app minimised, no signal); excluded only those who left ("Leave arena") or closed the app (`presence_disconnect` after their last heartbeat). Each user sees their own passive vote from the start of the battle (`get_my_passive_vote`, softer glow + "Your passive vote" on the card); voting any song replaces it (the same song = their active vote; tapping again cancels = abstain); it is cast for real at lock-in. Follow those, not the older conflicting docs. Built in steps 8+9; Paso_1 §8 "never reverses a clear win (≥2 active)" was explicitly **not** adopted (user, 2026-10-27).
- Queue tables: `queues` is wired for active proposals only (`integrations/supabase/proposals.ts`, shared by the Battle Room modal and the `/a/:code/propose` screen via `ProposeSongPanel`). Since step 6 proposals are Spotify tracks: `spotify-host` `search` (arena host's token or, step 7, the member's own; members only, ≤10 results) and `propose` (re-reads the track from Spotify, service-only `upsert_spotify_song`, then inserts `queues` **as the caller** so RLS/proposer stamp/presence still apply); `search_songs` (library) is dropped. `queues.proposed_by` is stamped from `auth.uid()` by a trigger (NULL for system inserts). `playlist_queue` (winners, `seq` order, `added_to_playlist_at`) is server-only since step 18 (RLS on, no client grants): it feeds the host's Spotify playlist.
- **Queue rules (step 12, `supabase/sql/queue_rules_2026-10-27.sql`, user decisions 2026-10-27):** all enforced in SQL, under a per-arena advisory lock (`lock_arena_queue`). `validate_queue_proposal` (BEFORE INSERT, ignores client `queue_type`/`position`/`priority`) refuses with P0001 + code as message (`spotify-host` `propose` returns them as `result`, `available_at` = hint): `in_battle`, `is_warmup` (lobby), `recently_played` (60 min after **sounding**: `playlist_queue.created_at` — winners, both songs of a draw — or `warmup_started_at`; losers never sounded; `track_available_at`), `proposer_queue_full` (5 queued per person), `queue_full` (10 `active` = the next 10 + 50 `waiting`). Order (`queue_ranked`): humans before system, then **turns per person** (songs already sent into battle + rank among their queued), then FIFO; a song in the next 10 never drops back. `pull_next_battle_songs` (battle 1 and every next battle): since step 17 the pair is the matchmaking's best pair of the next 10 (see "Matchmaking"); a slot without a human of another proposer → `pick_fallback_song` (**two songs actively proposed by the same person never face each other**, user decision 2026-10-29, `supabase/sql/no_self_battles_2026-10-29.sql`: no "same proposer's next"; the fallback's revancha and purged/withdrawn steps skip songs originally proposed by the other slot's proposer, `song_original_proposer`; a lone proposer's songs fight the host's backup music/reserve, then (user decisions 2026-10-29, `host_profile_songs_2026-10-29.sql` + `fair_play_2026-10-29.sql`) `pick_member_profile_song`: a track from the own MF affinity signals in other arenas of **any present member** with an account (`participant_presence` active/passive), ranked by fit then `presence_taste`, mapped by ISRC to a known Spotify track, copied into this arena as a system song ranked by fit, never fighting now/in the last battle; else the arena waits) (step 12b, `supabase/sql/host_fallback_songs_2026-10-27.sql`): a previous loser of this arena, not from the battle that just ended, and only once: never a song that already fought twice here (`pick_rematch_song`, user decision 2026-10-30, `rematch_once_2026-10-30.sql`) → the host's source chosen at creation (`arenas.fallback_source`: Liked Songs default or an own/collaborative playlist) → catalog search with the host's token by the first artist of this arena's proposed/winning songs and the warm-up → songs proposed here that were purged/withdrawn. Those two Spotify sources live in `arena_song_reserve` (service-only, ≤3 each, system songs that never enter `queues`), kept by `spotify-host` `refillReserve` at Start and on every watch tick (`reserve_needs`/`add_reserve_songs`). A pair is applied only when complete (else nothing changes); then +1 `battles_waited` on waiting rows and purge at 20. No pair = no battle: the arena "waits for songs" and `battle_lifecycle_job` calls `create_next_battle` every second for active arenas without an open battle (duration = last battle's playlist entries, or the warm-up for battle 1; `start_arena_battles` may return NULL). The **curated library is retired** (user decision 2026-10-27: test data only, songs `status = 'retired'`, never picked). Not chosen: winners again after 60 min, immediate rematch. `get_arena_queue_summary` (members): `human_queued` (< 4 → "The queue is running low" in Battle Room/Propose; count in the host Lobby) and `waiting_for_songs`. Songs leaving the queue go to `proposal_history` (battled/purged/withdrawn, server-only; a battles trigger links `battle_id`; outcome read from `battles`; step 15 PI reads the proposer from here; merged with accounts, purged with votes). `withdraw_proposal` (owner, still queued). `get_my_proposals` = queued (next/waiting + place + battles_left) then history (competing/won/lost/draw/cancelled/purged/withdrawn).
- **Song proposing/voting is a three-tier model, confirmed against `Dev/Backend/Music_Fighter_Backend_Block_3_Flows_Corrected.txt` §4-5 and `MUSIC FIGHTER — MVP CONSOLIDADO (TXT) v 3.2.txt` — don't re-derive this from memory, re-read those if unsure:** (tiers 2 and 3 describe the *pre-2026-10-27 spec*: their Spotify data sources and venue history are obsolete and both are to be redefined on Music Fighter's own data; the tier structure, human-first priority and the "no votes row = didn't vote" rule still stand.)
  1. **Active proposal** — a present user or the host explicitly submits a song (1 per user per battle); a duplicate is a pre-assigned vote (step 14, below). This is the only tier implemented so far (`ProposeSongPanel`, in the Battle Room modal and the Propose screen → `queues`).
  2. **Passive proposal** — NOT a participant action: the *system* fills a battle only when human proposals can't make a pair, always behind tier 1. **Built as step 13 (2026-10-28)** on MF's own data, not the old spec's Spotify affinity + `mood` + venue history (all obsolete): the fallback reserve ranked by fit with the arena + guests' lent Liked Songs, see "System songs that fit the arena". Pre-filling `queues` with system rows (`active_10 < 10`) was **not** chosen (user, 2026-10-28).
  3. **Passive voting** — at battle lock-in, any present user who didn't cast an explicit vote gets one computed from Music Fighter's own affinity score (step 8; the old Spotify `0.4·artist + 0.3·genre + 0.3·audio-features` formula is obsolete). **Built** (steps 8+9): `cast_passive_votes` at lock-in writes `vote_type = 'passive'`, summed by `calculate_lockin_vote_totals`. **"Didn't vote" means no `votes` row at all for that battle** (user decision, 2026-10-26): a participant who cast an explicit vote and then toggled it off (row with `status = 'cancelled'`) has *abstained* and must NOT receive a passive vote.
  Music Fighter is explicitly **not** a playback platform — the host's streaming connection is for audio output on the host's own device only; there is no participant streaming connection (dropped 2026-10-27). A `song_likes` table (manual in-app "like" tap, 3-like auto-queue threshold) was built in this session on the wrong premise before this distinction was caught — the 3-like auto-queue trigger was dropped in steps 8+9 and likes are now a manual own-affinity signal (`toggle_song_like`).

## Architecture

### Stack

Vite + React 18 + TypeScript, react-router-dom for routing, shadcn-ui (Radix primitives) + Tailwind for UI (`src/components/ui/*` is generated shadcn boilerplate — treat as vendor code, prefer composing over heavily editing), TanStack Query is wired up (`QueryClientProvider` in `App.tsx`) but most data access currently bypasses it in favor of direct Supabase calls + realtime subscriptions. Supabase is the backend: Postgres + Realtime + RPCs + a single Edge Function + anonymous auth.

Path alias `@/*` → `src/*` (see `vite.config.ts`, `tsconfig.json`, `components.json`).

### Screen flow

Routes in `src/App.tsx`, gated by `useAnonymousAuth` (every visitor gets a Supabase anonymous session before any route renders). **The arena travels in the URL as its `arena_code` (`/a/:code/...`, helpers in `src/lib/arenaRoutes.ts`), never in router state**, so reload/back/shared links work. Two zones (user decision 2026-10-26: Paso_2 §3 "no free navigation / no back / no menus" applies **only inside the Battle Room**):

- **App zone** — `components/nav/AppShell` with a bottom tab bar (Home · Propose · Arena · Ranking · Profile): `/` `SplashScreen` (+ "Back to <arena>"), `/join` and `/join/:code` (what the lobby QR encodes; auto-joins), `/create`, `/ranking` and `/profile` (placeholders; Profile holds "Leave arena"), `/a/:code/lobby` and `/a/:code/connect` (host only, others redirected to battle), `/a/:code/propose` (members only).
- **Battle Room** `/a/:code/battle` — no tab bar; only "← App" (switches screens, does NOT leave the arena), host "Lobby", End Arena. Entering it is the (re-)join (`ensureParticipant`).
- `/a/:code/stage` `StageViewScreen` — the party's shared screen (TV/projector) from a shared link, read-only, real data since step 19a (see "Stage View").
- Old `/battle`, `/lobby`, `/stage`, `/connect` and unknown paths redirect to `/`.

Host-ness is `arenas.host_id === auth.uid()` (`useArenaFromRoute`), the same rule RLS enforces on `participants.is_host` — never trust a client-side role flag. "Current arena" (tabs, Home shortcut) is backend-owned: `get_current_arena()` = most recent open arena the user is in and hasn't left; "Leave arena" (`leave_arena`) sets `participants.left_at` (explicit exit, Paso_2 §4.1; step 3/4 presence should treat it as INACTIVO), re-entering clears it. Browsing other app screens keeps the user in the arena. Definitions: `supabase/sql/navigation_2026-10-26.sql`.

Presence (step 3, `supabase/sql/presence_tracking_2026-10-26.sql`): `participants.last_active_at` is written **only server-side** — `enter_arena(p_arena_id)` (what `ensureParticipant` calls on every Battle Room / host Lobby entry; insert-or-touch, clears `left_at`, decides `is_host` itself), AFTER triggers on `votes` (cast, switch, toggle-off; never `passive`) and `queues` (rows with `proposed_by`), and the host's Start battles (arenas waiting → active). A BEFORE trigger on `participants` pins `last_active_at`/`joined_at`/identity columns for client roles (`anon`/`authenticated`), so writing them from the frontend is silently ignored — add new activity sources as SECURITY DEFINER triggers/RPCs calling `touch_participant_activity` (not client-callable). A heartbeat is not activity (v4 §1.3).

Presence states (step 4, `supabase/sql/presence_states_2026-10-26.sql`): ACTIVO/PASIVO/INACTIVO are **computed on the fly** by `presence_state(...)` (exposed as the `participant_presence` view, `security_invoker`), never stored and never decided by the frontend. ACTIVO = action in the last 5 min; PASIVO = connected, no action in 5 min; INACTIVO = `left_at` set, arena not open, `presence_disconnect` (tab closed, `pagehide`) or no heartbeat for 10 min. "Connected" is `participants.last_seen_at`, written by `presence_heartbeat()` every 30 s from any app screen except the Stage View (`usePresenceHeartbeat` in `App.tsx`); it acts on the caller's current arena (same rule as `get_current_arena`), never touches `last_active_at`, and doesn't keep arenas alive. Activity (`touch_participant_activity`, `enter_arena`) also refreshes `last_seen_at`. A trigger on `battles.lockin_at` freezes everyone's state into `battle_presence_snapshots` (read-only for clients, purged with votes) — **step 9 (passive vote) and the 0.4/0.5 PB ratio must read that snapshot, not the live view**. User decisions 2026-10-26: no linked music account required to be PASIVO (it's a step-9 condition for producing a passive vote); "ACTIVO→PASIVO mid-battle keeps the vote but can't change it" = the vote keeps counting as active and is never replaced by a passive one, and tapping again is an action (back to ACTIVO, change accepted) — no RLS lock. Re-entering = ACTIVO (v4 over Paso_1 §3.3). Spec conflict left for step 9: the 0.5 PB threshold is "≥75 % pasivos" in v3.2/v4 but "≥75 % inactivos" in Paso_1/PRD — the snapshot keeps all three states so either works. Display: `get_arena_presence` (own state + counts, members/host only), `PresenceChip` in the Battle Room, counts in the host Lobby.

Optional accounts (step 7b, `supabase/sql/accounts_2026-10-27.sql`, `integrations/supabase/account.ts`, `AccountPanel` in Profile, `/privacy`): email + 6-digit code only (user decisions 2026-10-27). New email → `updateUser({email})` + `verifyOtp(type email_change)`: same `auth.uid()`, nothing moves. Email that already has an account → `create_merge_ticket()` (as the anonymous user, single use, 10 min) + `signInWithOtp(shouldCreateUser:false)` + `verifyOtp(type email)`, then `spotify-host` `merge_anonymous` **fuses** the anonymous user into the account (user chose merge over discard): Spotify connection re-encrypted for the new id (anonymous side wins only if the account has none or it hosts an open arena), then service-only `merge_anonymous_user` moves arenas/playback/participants/votes/likes/snapshots/proposals (same arena on both sides: account row kept, most recent vote per battle kept, presence combined) and the anonymous auth user is deleted. `delete_account` ends hosted open arenas, deletes Spotify data and the auth user (arena rows keep the dangling id). Consent per policy version in `privacy_consents` (`record_privacy_consent`). Auth config needed (dashboard): site URL/redirect allowlist, OTP length 6, `{{ .Token }}` in the Magic Link and Change Email templates, custom SMTP (built-in only mails project members, 2/h).

Arena/participant identity: the identity anchor **is the Supabase auth user id** (`auth.uid()`, from the anonymous session; `getOrCreateIdentityAnchor` just returns it). The old `identity_anchors` table was dropped in step 19 (`supabase/sql/cleanup_identity_anchors_2026-10-29.sql`); the `identity_anchor_id` column names stay and hold `auth.uid()`. `participants` (`ensureParticipant`, idempotent insert-or-fetch keyed by `arena_id` + `identity_anchor_id`) establish who's in an arena and whether they're the host.

### Host Spotify connection (step 5, `supabase/sql/spotify_host_connection_2026-10-27.sql`)

One connection per **user** (`streaming_accounts.host_id = auth.uid()`), reused by all the arenas they host; anyone can connect from Profile (`/profile`), Create Arena or the host's Connect screen. A guest's connection is not used in other people's arenas — except the planned, unbuilt "propose from my own playlists / search with my account" (roadmap step 7), never for affinity or passive votes. Only the `spotify-host` Edge Function (service_role; deployed with `--no-verify-jwt`, it validates the caller's JWT itself) touches `streaming_accounts`/`spotify_oauth_states`: RLS on, no policies, no client grants. Tokens are AES-256-GCM-encrypted **in the function** (`SPOTIFY_TOKEN_KEY` Edge secret, versioned `v1:` prefix, AAD = host id + column) — never decrypt or write tokens from SQL, and never send them to the client. The client sees `get_my_streaming_connection()` (stored summary, no tokens) and the function's `status` (summary + live devices). Edge secrets: `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET`, `SPOTIFY_TOKEN_KEY`, `SPOTIFY_REDIRECT_URIS` (comma-separated allowlist, must match the Spotify dashboard exactly; set to 127.0.0.1:8080, `creative-cue-codex.lovable.app` and the Lovable preview `id-preview--8e019720-a933-46e4-b1d2-8ce34428b259.lovable.app`, each + `/spotify/callback`, no spaces; a new Lovable domain fails Connect with "Not a registered redirect URI" until it is added here **and** in the Spotify dashboard. Lovable's newer preview domain `preview--creative-cue-codex.lovable.app` is deliberately **not** registered (user decision 2026-10-29: Spotify is connected from the published app); Spotify rejects `localhost`). The anonymous session is per origin, so connect Spotify and host the arena from the same domain.

- Scopes: `user-read-playback-state`, `user-modify-playback-state`, `playlist-modify-private` + (step 7) `playlist-read-private`, `user-library-read` + (likes, 2026-10-27) `user-library-modify` + (2026-10-28) `user-read-private`, only for `GET /me` `country` (`streaming_accounts.country`). Older connections keep working (soft re-consent: `status.can_read_library`/`can_save_likes`/`can_check_market = false` → "Reconnect Spotify" in Profile; `can_read_library` also in "My playlists"); reconnecting the same Spotify account keeps the chosen device/Premium check.
- PKCE: verifier/state generated server-side, bound to the user, single-use, 10 min. `/spotify/callback` (`SpotifyCallbackScreen`) posts code+state back and returns to `return_to` (relative paths only). Token exchange uses Basic auth + `code_verifier`.
- Refresh is on demand in the function (60 s before expiry); `invalid_grant` = access revoked → the connection is deleted.
- Premium: `GET /me` no longer has `product`, so `premium_status` (`unverified|premium|not_premium`) is learnt from the player API — a transfer with `play:false` (connect-time to the already-active device, and on device selection); `403 PREMIUM_REQUIRED` = not Premium.
- Disconnect deletes every Spotify datum we store (policy I.1.2), incl. per-arena playlist/device ids (`forget_host_spotify`, also on `invalid_grant`), and pauses the host's running arenas; the playlist itself stays in their Spotify account (unfollowing is no longer in the API anyway). Spotify has no revoke endpoint, so the UI links to spotify.com/account/apps.

### Playback (step 6, `supabase/sql/spotify_playback_2026-10-27.sql`)

- **Playback Provider** (`supabase/functions/spotify-host/playback.ts`): provider-neutral `getStatus/play/queue/skip/onProgress` (+ `createSession` = the arena playlist, `search`, `getTrack`), `SpotifyPlaybackProvider` the only implementation. It runs only inside `spotify-host` (tokens never leave it). `queue` appends to the arena playlist (not Spotify's player queue; used since step 18); `skip` is unused (MF never skips; the host's skips are handled, see step 18).

Clients read `get_arena_playback` (pause for members, device/playlist link for the host) via `useArenaPlayback`.
- **Watcher = onProgress**: `spotify_playback_watch_job` (pg_cron, 15 s, pg_net → `spotify-host` `watch`, no JWT; each arena checked at most every 12 s so extra calls are harmless; `SPOTIFY_WATCH_SECRET` Edge secret + Vault `spotify_watch_secret`, same value, set 2026-10-27: `watch` without the `x-watch-secret` header gets 401; to rotate, update both, Vault first). **Pause rules (user decisions 2026-10-27):** while music is expected, 2 consecutive checks (~30 s) of no usable device (`device_lost`), Spotify paused (`playback_paused`) or playing outside the playlist (`off_playlist`) → `pause_arena`; host disconnected/revoked → `spotify_disconnected` immediately. Moving playback to another device of the host's = adopted, not a pause. **Resume is automatic**: device/connection back → MF plays the playlist again from the resume point (recreating the playlist if a disconnect cleared it); paused/off-playlist → when the host plays the playlist again; the host also has "Resume on Spotify" (`resume_arena` action). Outside the expected window nothing pauses. Since step 18 "music expected" comes from the sound plan (below), not from `expected_until` (display only).

- Spotify policy check (2026-10-27): no Policy/Terms clause forbids serving guests' catalog searches with the host's token (not personal data, token stays server-side, private non-commercial use); Spotify is moving away from Client Credentials for metadata, so the host token is the stable path. Keep attribution (logo, uncropped artwork, "Open Spotify" link: `SpotifyTrackRow`) and don't offer metadata as a standalone service.

### Real playback (step 18, `supabase/sql/real_playback_2026-10-28.sql`, user decisions 2026-10-28)

- **Sound plan** (`arena_sound_plan`, service-only): the warm-up, then every `playlist_queue` row by `seq`. Battle N plays during battle N−1's winners (battle 1: the warm-up) and lasts them (`create_next_battle`); the soundtrack is **anchored on the open battle's `started_at`**, so moving the open battle moves the plan. A battle's winners are planned at its end. `arena_playback_plan(arena, at)` = the entry expected now/at the pause, position, neighbours, open battle, `control_mode`; "music expected" = some entry is expected.
- **Appending**: winners are inserted when decided (lock-in, or Sudden Death at end − 5 s; draw = A then B in one statement); a statement trigger calls `nudge_spotify_host` (pg_net → `spotify-host` `nudge`, `x-watch-secret`), which claims (`claim_playlist_appends`, release on failure) and appends in order; every watch tick retries. Battle completion (and a late battle starting) also nudges. `ensureSession` recreates the playlist with every entry. `begin_playback_check` = one check per arena (watch 12 s, nudge 1.5 s).
- **Clock follows the music**: `sync_arena_clock(arena, track_uri, started_at)` re-anchors the open `arena` battle on the plan entry playing (closest planned start; soundtrack or its own winners: a skip forward ends it early, v4 §8.3), drift < 1 s ignored (was 3 s; Spotify's progress is timed at the middle of the status request, `PlaybackStatus.observedAt`), warm-up shifted with battle 1. ±5 s at song changes is not a change (`SEAM_MS`).
- **Late battles** (the arena waited for songs): `battles.soundtrack = 'autoplay'` when what's left of its soundtrack is < 60 s → 60 s battle over Spotify's Autoplay/silence (nothing expected, nothing pauses); `fit_battle_to_track` stretches it once to the end of the Autoplay track if that leaves ≥ 60 s. A song due < 20 s ago that Spotify isn't on (Autoplay, stopped) is started by MF from 0 ("kick"). **A song already playing is never cut** (user decision 2026-10-28): if Spotify's Autoplay/radio began before an arena song was due (the previous song ended before the winner reached Spotify's queue, or a late battle's Autoplay track is still playing), `autoplay_lead_in` gives that song a lead-in (`playlist_queue.lead_in_ms` = the radio time before it, in the plan and in `create_next_battle`'s duration), lengthens the battle playing over it, and sets `arena_playback.wake_at` = the radio track's end; `battle_lifecycle_job` (every second) calls `wake_spotify_host()` → nudge → the song is kicked right after the radio track. The lead-in follows the radio track really playing (`playlist_queue.lead_in_track_uri`, `supabase/sql/radio_follow_2026-10-28.sql`): the same track = its real end (seeks), another radio track = the song starts at once (`kick: true`). Once per song, capped at 10 min. **Real lengths**: while an arena song plays, `correct_track_duration` replaces its stored length with Spotify's (relinked versions differ; a shorter one made the previous song end ~5 s early) and adjusts the battle over it (`adjust_battle_duration`, floors: lock-in 25 s / Sudden Death 10 s ahead). The player is the source of truth for length (stored lengths come from the Spotify API, which may describe another version; ISRC/MusicBrainz don't help): the previous arena song still playing the same playthrough (started on `prev_planned_start` ±5 s) past its planned end is a longer version, not a manual change — it finishes and its length is corrected (`supabase/sql/real_lengths_2026-10-28.sql`); corrections are logged (`real length`).
- **Manual changes** (`arena_playback.control_mode`): `auto` = a skip/back/reorder/hand-added song inside the playlist, or skipping past its end, → MF plays the expected track at its point and sets `manual_change_at` (host prompt in `NowPlaying`); `manual` (host confirmed, whole arena, `set_arena_control_mode`) = skips forward re-time the battle, skipping past the end = `skip_to_lockin`, anything else = `off_playlist`. Pausing Spotify / another playlist = step-6 pause in both modes. Arena finished = Spotify plays out the playlist.
- **Songs unplayable in the host's country** (`supabase/sql/unplayable_tracks_2026-10-28.sql`, user decisions 2026-10-28; found in-app: a greyed-out winner made MF put it back every 15 s): prevention = every catalog call passes the **arena host's** country as `market` (also a guest's own-account search/playlists: the music plays in the host's country), so `CatalogTrack.is_playable` marks them (`SpotifyTrackRow` greys them out; **search never shows them**: with `market` Spotify's search only returns content available there — user decision 2026-10-28: keep it that way; the grey label shows in own playlists/Liked Songs), `propose` returns `not_available`, the warm-up is refused and the reserve skips them; unknown country (old connection) = not checked. Runtime: when Spotify isn't on the expected track, `checkArena` asks `getTrack` with the market (or, country unknown, 2 put-backs of it in a row didn't stick: `arena_playback.put_back_uri/count`) → `skip_unplayable_track` marks it (`playlist_queue.unplayable_at` / `arenas.warmup_unplayable_at`: duration 0 and not `added` in the plan, ignored by `create_next_battle`) and shortens the battle playing over it by its length (floor: lock-in 15 s ahead, i.e. last song = lock-in now); MF plays the next expected song, no pause, no host prompt; `get_arena_playback.unplayable_title` (2 min) → "isn't available in the host's country: skipped".
- **Track relinking**: Spotify's player may report another id for a playlist track (same recording, the version for the host's country; the Web API with `market` can still return the original id). `checkArena` maps an unknown uri on the playlist back to an arena song (`arenaUriFor`: Spotify relinking the expected song to that id with the host's `market`, else same ISRC, else same title + first artist + length ±20 s (2026-10-28: Spotify's player played one song as two other releases, other ISRCs, +6 s/+16 s, and MF took them for Autoplay → pause + lead-in), else the expected song's length playing at its planned point ±10 s) before comparing it with the plan; unmatched ones are logged (`unknown track on the arena playlist`); an unmatched track that isn't in the playlist either (`playlistHas`) is Spotify's **Autoplay/radio, which reports the arena playlist as its context** (found in-app 2026-10-28) and counts as off the playlist; Autoplay in the expected song's last 5 s is its natural end, not a manual change (no prompt, nothing cut: the lead-in above); without it MF kept "putting back" the song and undid the host's seeks (found in-app 2026-10-28).
- **Display**: `get_arena_playback` adds now playing (arena song on the player, else the one due), next, `player_context`, `control_mode`, `manual_change_at` (host); `NowPlaying` in the Battle Room and host Lobby.

### Backend-authoritative battle state machine — the core design invariant

This is the most important architectural rule in the codebase, stated repeatedly in comments across the source: **the frontend never computes votes, winners, timing, or phase transitions — it only derives display state from fields already decided by the backend.** All battle lifecycle logic (lock-in timing, sudden death, winner resolution) lives in SQL (RPCs + a cron job), not in React.

- `battles.state` is the source of truth: `"pending" | "active" | "closing" | "completed"`.
- Related backend fields consumed read-only by the frontend: `started_at`, `duration_ms`, `lockin_at`, `sudden_death_active`, `resolution_type`, `winner_song_id`, `had_sudden_death`.
- `src/lib/battleClosureOrchestrator.ts` — pure functions that *derive* display phase/winner from a `BattleData` row (`deriveVotingPhaseFromBattle`, `getWinnerFromBattle`, etc.) plus `emitBattleClosedEvent`/`emitLockinReachedEvent`/`emitSuddenDeathStartedEvent`, which dispatch `window` CustomEvents (`battle:closed`, `battle:lockin_reached`, `battle:sudden_death_started`) that hooks listen for to know when to re-sync from the backend.
- `src/hooks/useBattleOrchestrator.ts` — owns the live `ArenaBattleView` (a view over `arena_live_state`, a Postgres view joining battle + song + vote-count data). Subscribes to Postgres realtime changes on `battles` filtered by `arena_id`; on INSERT it optimistically renders a minimal row (carrying over previous song metadata as placeholder) then backfills the full view row async; on UPDATE it merges a fixed allowlist of fields (`MERGE_FIELDS`). Vote counts are additionally polled every 2s (realtime isn't relied on for vote tallies).
  - `arena_live_state` exposes the battle state as **`status`**, not `state`; `normalizeViewRow` maps it. Every read of the view must go through it, or `battle.state` is silently `undefined` and voting never enables. Its `votes_a`/`votes_b` count only `status = 'active'` votes, and only `sudden_death` votes once a battle has entered Sudden Death (`sudden_death_started_at` set), so the bar matches the tally that decides the winner.
- `src/hooks/useBattleClosureOrchestrator.ts` — separate, narrower snapshot (`ClosureStateSnapshot`) fetched straight from `battles` table, used specifically to detect resolution/lock-in/sudden-death and drive `useArenaFlow`.
- `src/hooks/useArenaFlow.ts` — consumes a resolved battle **exactly once** per `battleId` (idempotency guarded via a ref, not state) to trigger post-battle UI/consequences.
- Battle-ended handling is entirely server-side (SQL cron + RPC); the old no-op `useBattleEndedTrigger` stub was removed in step 19. To react to a battle ending in the UI, use the closure-orchestrator/event path.
- `src/lib/derivedBattlePhase.ts` `getDerivedBattlePhase()` (Battle Room and Stage View) maps backend state → a UI-only `DerivedBattlePhase` (`NORMAL | FINAL_30S | LOCK_IN | SUDDEN_DEATH | RESULT | FINISHED`; `FINAL_30S` = the 30 s before the scheduled lock-in, from `started_at`/`duration_ms`; `RESULT` = closing with `resolution_type` set, i.e. decided at lock-in or at Sudden Death's close, still playing) used purely for rendering (overlays, tension bar intensity) — this is a second, display-only derivation layered on top of the orchestrators above, not a competing source of truth. `src/hooks/useBattleDisplay.ts` wraps it for both screens: it re-renders when `FINAL_30S` opens and keeps the finished battle on screen `BATTLE_HOLD_MS` after the next one is created (the backend completes and creates in one statement), returning `isLive` so votes only go to the live battle.
- Step 19c (Paso_2 §5-7, 2026-10-30, all display): `TensionBar` (rAF on the DOM, eases to the backend points, labels pinned to the divider, micro-oscillation by intensity), `StageView` (the card square is the vote button via `onVote`; resolution sequence with the Web Animations API: loser out by its side, winner centred + scaled, bounded to the cards' area; draw = both stay + glow), `BattleStateOverlay` (messages over the timer row, never over the bar or Spotify artwork; only WINNER/DRAW block the battle surface). Don't put anything over the artwork or the bar.
- `src/integrations/supabase/votes.ts` (`applyVoteIntent`) re-fetches `lockin_at`/`sudden_death_active` from the DB on every vote and enforces phase rules there — the `_isLockedIn` parameter passed in is explicitly ignored/deprecated. RLS rejections are treated as "vote locked" rather than a hard error (`isRlsError`).
- `supabase/functions/battle-finalizer-cron/index.ts`, `battle-lockin`, `battle-ended` — legacy Edge Functions, dead (the `run_battle_finalizer_job` RPC no longer exists; the other two only read a battle); the lifecycle runs in pg_cron `battle_lifecycle_job`. The SQL definitions live in `supabase/sql/` files applied by hand; the RPC/cron-job definitions and DB schema/migrations live in the Supabase project itself, not in this repo (`supabase/` has no `config.toml` or migrations directory).

When touching anything battle-related: resist adding client-side timers/logic that *decide* outcomes. Timers in the UI (e.g. `BattleTimer`) are display-only countdowns computed from backend `started_at`/`duration_ms` and must never gate voting or transitions themselves — always gate on `battle.state` (or the derived phase built from it).

The phase-desync debug logging (`[BattleTimer Debug]`, `[DerivedPhase Debug]`, `[Realtime Debug]`, `[StageView Render]`) was removed in step 19; don't add per-tick/per-render logging back.

### Supabase integration layout

`src/integrations/supabase/` — one file per concern, all thin wrappers around `supabase-js` calls (no ORM/repository abstraction beyond this):
- `client.ts` — Supabase client singleton (anon key, safe to expose client-side)
- `arenas.ts`, `participants.ts`, `identityAnchors.ts`, `votes.ts` — CRUD/RPC calls for each entity

RLS invariants (who may vote when, Sudden Death immutability, arena-state gating) are **restrictive** policies on purpose: permissive policies OR together, *including their WITH CHECKs independently of which policy matched the row*, which silently defeated the old "block" policies on `votes`. Also note an UPDATE policy without WITH CHECK reuses its USING for the new row. Verify RLS changes with a rollback smoke test (`do $$ ... raise exception $$` as `authenticated`), not by reading policy text.

Mutations that need cross-row invariants (creating an arena, resolving battles) go through Postgres RPCs (`create_arena`, `run_battle_finalizer_job`) rather than raw inserts, keeping that logic server-side alongside the battle state machine.
