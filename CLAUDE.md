# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Music Fighter" — a real-time, arena-style music battle app for **private gatherings among friends** (not bars/venues). A host creates an arena, participants join with a code, and songs face off head-to-head while participants vote from their phones. A separate "stage view" renders the battle on a shared screen (TV/projector).

This is a **Lovable** project: it is edited both locally and via the Lovable web editor (lovable.dev), and changes from either side sync through this git repo. `.lovable/plan.md` holds the description of the most recently applied Lovable change — treat it as a scratch note, not documentation, and expect it to be overwritten/irrelevant across sessions.

## Business Rules (from project spec, not inferable from code)

- **Change of focus (user decision 2026-10-27, after Spotify's Developer Policy) — overrides the spec docs wherever they disagree; full list of obsoleted spec parts in `docs/MVP_ROADMAP_2026-10-26.md` → "Change of focus":** (1) private gatherings, not venues — ignore spec wording about "local", venue history, GPS/geofencing, Stage View authenticating "the venue's account"; (2) Music Fighter **never plays audio**: it curates a playlist it creates in real time in the **host's Spotify Premium account**, played by the host's own Spotify app/device; (3) **participants never connect Spotify** — affinity/passive voting will come from Music Fighter's own data (roadmap steps 7-9 and 13 are "to be redefined": don't build them from the old spec, ask first); (4) **Jukebox Boost and all payments are excluded** (steps 10-11). Spotify's own data limits also apply: no audio features/recommendations (closed to new apps), no `popularity` and no `product` on `GET /me` (Feb 2026), search `limit` ≤ 10, `/playlists/{id}/items` (not `/tracks`), `POST /me/playlists`, dev mode = 5 allowlisted users. Spotify brand rules for any UI showing Spotify content: Spotify logo next to the metadata, artwork uncropped/uncovered, "OPEN SPOTIFY" link back, no crossfade/mixing (policy III.7).

- Arena states: waiting → active → finished, plus technical expired (Backend_Block_2 §1). Backend-only transitions: `create_arena` (→ waiting, mood required), `start_arena_battles` (host, waiting → active), `end_arena` (host, waiting|active → finished), `arena_expiry_job` cron → `expire_stale_arenas` (waiting idle 6h → expired; active idle 2h → finished, except the curated-library arena). "Idle" = no participant activity (joins, proposals, votes — battles don't count, the cron creates those). Finishing an arena closes its open battle: kept if already decided at lock-in, else `resolution_type = 'cancelled'` (no winner, nothing queued). Retention (Block 5 §6): `arena_vote_purge_job` daily snapshots each battle's `final_votes_a/b` and deletes individual votes 30 days after a finished/expired arena closes (`arenas.votes_purged_at`). Enforced server-side by a battles-insert trigger (battles only in active arenas) and restrictive RLS (votes only in active; joins/proposals only in waiting|active; expired hidden). Definitions: `supabase/sql/arena_state_model_2026-10-26.sql` + `arena_lifecycle_closure_2026-10-26.sql`. `arenas.mood` is fixed at creation and is UX/copy only — never let it affect battle rules.
- **Warm-up song (user decision 2026-10-26, overrides Backend_Block_2 §4 / Block_4 §2 "warm-up always ends before the first battle"):** the host picks it at creation (`create_arena(p_name, p_mood, p_warmup_song_id)`, required; suggestions = curated library, arena mood first via `songs.moods`). It is silent in the lobby. `start_arena_battles` (now returns the open battle id and creates battle 1 itself; the `create-battle` Edge Function is no longer called) sets `arenas.warmup_started_at` and battle 1's `duration_ms` = the warm-up's duration — the warm-up is the "winner of battle 0", playing during battle 1, the same rule the cron applies afterwards (duration = previous winner). Stored as the arena's own `songs` row with `role = 'warmup'`; triggers reject it in `queues`/`battles`, and it never scores/PI. The same library track may still be proposed (only the warmup row is excluded). Until step 6 the host's Battle Room browser is the provisional playback device (`useArenaWarmup`, signed URL from the private `curated-songs` bucket, readable only by the host while the arena is active). **Final product (user decision 2026-10-27, built in step 6):** the warm-up is the **first track of the arena's Spotify playlist** (created at Start, private, "Music Fighter · <arena> · dd/mm/aa") playing on the host's chosen device; it is then picked from Spotify search, so the host connects Spotify before creating an arena, and the browser MP3 goes away. The curated library's `spotify_track_id` values are placeholder UUIDs, not real Spotify ids. Definitions: `supabase/sql/warmup_song_2026-10-26.sql`.
- Battle states: pending → active → closing → completed. Backend-only transitions via SQL RPC + cron (run_battle_finalizer_job).
- Sudden Death: triggered when closing + tie at lock-in. Only sudden_death vote_type accepted; one immutable vote per participant; a prior regular vote can be upgraded once, never downgraded.
- Draw resolution: if still tied after Sudden Death, current spec (v3.2/v4) sends both songs to the queue in A-B order. Do not implement the older v3.0 tie-break logic (PI level, then random) — it's superseded.
- Vote types: "regular" (active phase) and "sudden_death" (closing + sudden_death_active). Regular votes can be toggled/switched; sudden_death votes are final once cast.
- Known open spec ambiguity: passive affinity timing and the k=1.25 affinity cap appear in some docs (Paso 1, PRD) but not others (v3.0, v4 consolidated). Do NOT implement affinity logic without checking with Sergio first — this is unresolved upstream, not a coding decision.
- Queue tables: `queues` is wired for active proposals only (`integrations/supabase/proposals.ts`, shared by the Battle Room modal and the `/a/:code/propose` screen via `ProposeSongPanel`). `queues.proposed_by` is stamped from `auth.uid()` by a trigger (NULL for system inserts); `get_my_proposals` lists the caller's still-queued proposals (rows are deleted when they enter a battle). `playlist_queue` still has zero frontend wiring.
- **Song proposing/voting is a three-tier model, confirmed against `Dev/Backend/Music_Fighter_Backend_Block_3_Flows_Corrected.txt` §4-5 and `MUSIC FIGHTER — MVP CONSOLIDADO (TXT) v 3.2.txt` — don't re-derive this from memory, re-read those if unsure:** (tiers 2 and 3 describe the *pre-2026-10-27 spec*: their Spotify data sources and venue history are obsolete and both are to be redefined on Music Fighter's own data; the tier structure, human-first priority and the "no votes row = didn't vote" rule still stand.)
  1. **Active proposal** — a present user or the host explicitly submits a song (1 per user per battle). This is the only tier implemented so far (`ProposeSongPanel`, in the Battle Room modal and the Propose screen → `queues`).
  2. **Passive proposal** — NOT a participant action. The *system* auto-fills empty queue slots (trigger: `active_10 < 10` or `waiting_50 < 50`) from aggregate passive-user Spotify affinity + the arena's `mood` + venue music history, always lower priority than tier 1 ("fill first with ACTIVE, then PASSIVE if necessary"). Unbuilt, and has three real prerequisites that don't exist anywhere in this codebase yet: participant-side streaming connection (today's `ConnectStreamingScreen`/`streaming_accounts` is host-only, for playback, not preference), `arenas.mood` actually being set/used (real column, currently dead), and venue-level music history (no schema for this at all).
  3. **Passive voting** — at battle lock-in, any present user who didn't cast an explicit vote gets one computed automatically from Spotify-profile similarity (`0.4·artist + 0.3·genre + 0.3·audio-features`, weighted bonus if score ≥ 0.7). This is the real source of `vote_type = 'passive'`, which `calculate_lockin_vote_totals` already sums alongside `'regular'` — the SQL anticipates this, the frontend doesn't produce it yet. **"Didn't vote" means no `votes` row at all for that battle** (user decision, 2026-10-26): a participant who cast an explicit vote and then toggled it off (row with `status = 'cancelled'`) has *abstained* and must NOT receive a passive vote.
  Music Fighter is explicitly **not** a playback platform — the host's streaming connection is for audio output on the host's own device only; there is no participant streaming connection (dropped 2026-10-27). A `song_likes` table (manual in-app "like" tap, 3-like auto-queue threshold) was built in this session on the wrong premise before this distinction was caught — it stays in place but disconnected/unused until the real Spotify-affinity mechanism above is built; don't extend it further in the meantime, and reconcile/replace it when participant-side streaming integration lands.

## Architecture

### Stack

Vite + React 18 + TypeScript, react-router-dom for routing, shadcn-ui (Radix primitives) + Tailwind for UI (`src/components/ui/*` is generated shadcn boilerplate — treat as vendor code, prefer composing over heavily editing), TanStack Query is wired up (`QueryClientProvider` in `App.tsx`) but most data access currently bypasses it in favor of direct Supabase calls + realtime subscriptions. Supabase is the backend: Postgres + Realtime + RPCs + a single Edge Function + anonymous auth.

Path alias `@/*` → `src/*` (see `vite.config.ts`, `tsconfig.json`, `components.json`).

### Screen flow

Routes in `src/App.tsx`, gated by `useAnonymousAuth` (every visitor gets a Supabase anonymous session before any route renders). **The arena travels in the URL as its `arena_code` (`/a/:code/...`, helpers in `src/lib/arenaRoutes.ts`), never in router state**, so reload/back/shared links work. Two zones (user decision 2026-10-26: Paso_2 §3 "no free navigation / no back / no menus" applies **only inside the Battle Room**):

- **App zone** — `components/nav/AppShell` with a bottom tab bar (Home · Propose · Arena · Ranking · Profile): `/` `SplashScreen` (+ "Back to <arena>"), `/join` and `/join/:code` (what the lobby QR encodes; auto-joins), `/create`, `/ranking` and `/profile` (placeholders; Profile holds "Leave arena"), `/a/:code/lobby` and `/a/:code/connect` (host only, others redirected to battle), `/a/:code/propose` (members only).
- **Battle Room** `/a/:code/battle` — no tab bar; only "← App" (switches screens, does NOT leave the arena), host "Lobby", End Arena. Entering it is the (re-)join (`ensureParticipant`).
- `/a/:code/stage` `StageViewScreen` — venue screen from a shared link, read-only; battle data still placeholder until step 19.
- Old `/battle`, `/lobby`, `/stage`, `/connect` and unknown paths redirect to `/`.

Host-ness is `arenas.host_id === auth.uid()` (`useArenaFromRoute`), the same rule RLS enforces on `participants.is_host` — never trust a client-side role flag. "Current arena" (tabs, Home shortcut) is backend-owned: `get_current_arena()` = most recent open arena the user is in and hasn't left; "Leave arena" (`leave_arena`) sets `participants.left_at` (explicit exit, Paso_2 §4.1; step 3/4 presence should treat it as INACTIVO), re-entering clears it. Browsing other app screens keeps the user in the arena. Definitions: `supabase/sql/navigation_2026-10-26.sql`.

Presence (step 3, `supabase/sql/presence_tracking_2026-10-26.sql`): `participants.last_active_at` is written **only server-side** — `enter_arena(p_arena_id)` (what `ensureParticipant` calls on every Battle Room / host Lobby entry; insert-or-touch, clears `left_at`, decides `is_host` itself), AFTER triggers on `votes` (cast, switch, toggle-off; never `passive`) and `queues` (rows with `proposed_by`), and the host's Start battles (arenas waiting → active). A BEFORE trigger on `participants` pins `last_active_at`/`joined_at`/identity columns for client roles (`anon`/`authenticated`), so writing them from the frontend is silently ignored — add new activity sources as SECURITY DEFINER triggers/RPCs calling `touch_participant_activity` (not client-callable). A heartbeat is not activity (v4 §1.3).

Presence states (step 4, `supabase/sql/presence_states_2026-10-26.sql`): ACTIVO/PASIVO/INACTIVO are **computed on the fly** by `presence_state(...)` (exposed as the `participant_presence` view, `security_invoker`), never stored and never decided by the frontend. ACTIVO = action in the last 5 min; PASIVO = connected, no action in 5 min; INACTIVO = `left_at` set, arena not open, `presence_disconnect` (tab closed, `pagehide`) or no heartbeat for 10 min. "Connected" is `participants.last_seen_at`, written by `presence_heartbeat()` every 30 s from any app screen except the Stage View (`usePresenceHeartbeat` in `App.tsx`); it acts on the caller's current arena (same rule as `get_current_arena`), never touches `last_active_at`, and doesn't keep arenas alive. Activity (`touch_participant_activity`, `enter_arena`) also refreshes `last_seen_at`. A trigger on `battles.lockin_at` freezes everyone's state into `battle_presence_snapshots` (read-only for clients, purged with votes) — **step 9 (passive vote) and the 0.4/0.5 PB ratio must read that snapshot, not the live view**. User decisions 2026-10-26: no linked music account required to be PASIVO (it's a step-9 condition for producing a passive vote); "ACTIVO→PASIVO mid-battle keeps the vote but can't change it" = the vote keeps counting as active and is never replaced by a passive one, and tapping again is an action (back to ACTIVO, change accepted) — no RLS lock. Re-entering = ACTIVO (v4 over Paso_1 §3.3). Spec conflict left for step 9: the 0.5 PB threshold is "≥75 % pasivos" in v3.2/v4 but "≥75 % inactivos" in Paso_1/PRD — the snapshot keeps all three states so either works. Display: `get_arena_presence` (own state + counts, members/host only), `PresenceChip` in the Battle Room, counts in the host Lobby.

Arena/participant identity: the identity anchor **is the Supabase auth user id** (`auth.uid()`, from the anonymous session; `getOrCreateIdentityAnchor` just returns it). The `identity_anchors` table is vestigial — nothing references it, and its RLS only allows the `anon` role (anonymous sign-ins are `authenticated`), so don't write to it. `participants` (`ensureParticipant`, idempotent insert-or-fetch keyed by `arena_id` + `identity_anchor_id`) establish who's in an arena and whether they're the host.

### Host Spotify connection (step 5, `supabase/sql/spotify_host_connection_2026-10-27.sql`)

One connection per **host user** (`streaming_accounts.host_id = auth.uid()`), reused by all their arenas. Only the `spotify-host` Edge Function (service_role; deployed with `--no-verify-jwt`, it validates the caller's JWT itself) touches `streaming_accounts`/`spotify_oauth_states`: RLS on, no policies, no client grants. Tokens are AES-256-GCM-encrypted **in the function** (`SPOTIFY_TOKEN_KEY` Edge secret, versioned `v1:` prefix, AAD = host id + column) — never decrypt or write tokens from SQL, and never send them to the client. The client sees `get_my_streaming_connection()` (stored summary, no tokens) and the function's `status` (summary + live devices). Edge secrets: `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET`, `SPOTIFY_TOKEN_KEY`, optional `SPOTIFY_REDIRECT_URIS` (defaults: `http://127.0.0.1:8080/spotify/callback`, `https://creative-cue-codex.lovable.app/spotify/callback`; Spotify rejects `localhost`, and Lovable preview domains aren't registered).

- PKCE: verifier/state generated server-side, bound to the user, single-use, 10 min. `/spotify/callback` (`SpotifyCallbackScreen`) posts code+state back and returns to `return_to` (relative paths only). Token exchange uses Basic auth + `code_verifier`.
- Refresh is on demand in the function (60 s before expiry); `invalid_grant` = access revoked → the connection is deleted.
- Premium: `GET /me` no longer has `product`, so `premium_status` (`unverified|premium|not_premium`) is learnt from the player API — a transfer with `play:false` (connect-time to the already-active device, and on device selection); `403 PREMIUM_REQUIRED` = not Premium.
- Disconnect deletes every Spotify datum we store (policy I.1.2); Spotify has no revoke endpoint, so the UI links to spotify.com/account/apps. Anything per-arena added later (playlist ids, step 6) must be cleared too.
- Step 5 does not pause arenas or gate Start on Spotify; that's step 6/18.

### Backend-authoritative battle state machine — the core design invariant

This is the most important architectural rule in the codebase, stated repeatedly in comments across the source: **the frontend never computes votes, winners, timing, or phase transitions — it only derives display state from fields already decided by the backend.** All battle lifecycle logic (lock-in timing, sudden death, winner resolution) lives in SQL (RPCs + a cron job), not in React.

- `battles.state` is the source of truth: `"pending" | "active" | "closing" | "completed"`.
- Related backend fields consumed read-only by the frontend: `started_at`, `duration_ms`, `lockin_at`, `sudden_death_active`, `resolution_type`, `winner_song_id`, `had_sudden_death`.
- `src/lib/battleClosureOrchestrator.ts` — pure functions that *derive* display phase/winner from a `BattleData` row (`deriveVotingPhaseFromBattle`, `getWinnerFromBattle`, etc.) plus `emitBattleClosedEvent`/`emitLockinReachedEvent`/`emitSuddenDeathStartedEvent`, which dispatch `window` CustomEvents (`battle:closed`, `battle:lockin_reached`, `battle:sudden_death_started`) that hooks listen for to know when to re-sync from the backend.
- `src/hooks/useBattleOrchestrator.ts` — owns the live `ArenaBattleView` (a view over `arena_live_state`, a Postgres view joining battle + song + vote-count data). Subscribes to Postgres realtime changes on `battles` filtered by `arena_id`; on INSERT it optimistically renders a minimal row (carrying over previous song metadata as placeholder) then backfills the full view row async; on UPDATE it merges a fixed allowlist of fields (`MERGE_FIELDS`). Vote counts are additionally polled every 2s (realtime isn't relied on for vote tallies).
  - `arena_live_state` exposes the battle state as **`status`**, not `state`; `normalizeViewRow` maps it. Every read of the view must go through it, or `battle.state` is silently `undefined` and voting never enables. Its `votes_a`/`votes_b` count only `status = 'active'` votes, and only `sudden_death` votes once a battle has entered Sudden Death (`sudden_death_started_at` set), so the bar matches the tally that decides the winner.
- `src/hooks/useBattleClosureOrchestrator.ts` — separate, narrower snapshot (`ClosureStateSnapshot`) fetched straight from `battles` table, used specifically to detect resolution/lock-in/sudden-death and drive `useArenaFlow`.
- `src/hooks/useArenaFlow.ts` — consumes a resolved battle **exactly once** per `battleId` (idempotency guarded via a ref, not state) to trigger post-battle UI/consequences.
- `src/hooks/useBattleEndedTrigger.ts` — deliberately a no-op stub, kept only so existing imports don't break. Battle-ended handling has moved entirely server-side (SQL cron + RPC). Don't resurrect logic here — if you need to react to battle end, use the closure-orchestrator/event path instead.
- `src/screens/BattleRoomScreen.tsx` has its own `getDerivedBattlePhase()` mapping backend state → a UI-only `DerivedBattlePhase` (`NORMAL | FINAL_30S | LOCK_IN | SUDDEN_DEATH | FINISHED`) used purely for rendering (overlays, tension bar intensity) — this is a second, screen-local derivation layered on top of the orchestrators above, not a competing source of truth.
- `src/integrations/supabase/votes.ts` (`applyVoteIntent`) re-fetches `lockin_at`/`sudden_death_active` from the DB on every vote and enforces phase rules there — the `_isLockedIn` parameter passed in is explicitly ignored/deprecated. RLS rejections are treated as "vote locked" rather than a hard error (`isRlsError`).
- `supabase/functions/battle-finalizer-cron/index.ts` — an Edge Function invoked on a schedule that calls the `run_battle_finalizer_job` RPC using the service-role key. This repo only contains the Edge Function; the RPC/cron-job definitions and DB schema/migrations live in the Supabase project itself, not in this repo (`supabase/` has no `config.toml` or migrations directory).

When touching anything battle-related: resist adding client-side timers/logic that *decide* outcomes. Timers in the UI (e.g. `BattleTimer`) are display-only countdowns computed from backend `started_at`/`duration_ms` and must never gate voting or transitions themselves — always gate on `battle.state` (or the derived phase built from it).

Note: several files currently contain verbose `console.log` debug instrumentation (`[BattleTimer Debug]`, `[DerivedPhase Debug]`, `[Realtime Debug]`, `[StageView Render]`, etc.) added for diagnosing phase-desync timing issues — see `.lovable/plan.md` for the rationale at the time it was added. Don't treat the presence of heavy logging as the norm to imitate elsewhere; it's task-specific debug scaffolding.

### Supabase integration layout

`src/integrations/supabase/` — one file per concern, all thin wrappers around `supabase-js` calls (no ORM/repository abstraction beyond this):
- `client.ts` — Supabase client singleton (anon key, safe to expose client-side)
- `arenas.ts`, `participants.ts`, `identityAnchors.ts`, `votes.ts` — CRUD/RPC calls for each entity

RLS invariants (who may vote when, Sudden Death immutability, arena-state gating) are **restrictive** policies on purpose: permissive policies OR together, *including their WITH CHECKs independently of which policy matched the row*, which silently defeated the old "block" policies on `votes`. Also note an UPDATE policy without WITH CHECK reuses its USING for the new row. Verify RLS changes with a rollback smoke test (`do $$ ... raise exception $$` as `authenticated`), not by reading policy text.

Mutations that need cross-row invariants (creating an arena, resolving battles) go through Postgres RPCs (`create_arena`, `run_battle_finalizer_job`) rather than raw inserts, keeping that logic server-side alongside the battle state machine.
